# Open the local SFlow browser workspace

SFlow can run an independent local service and open its browser workspace. VS Code is a client of
the service; opening it does not reopen folders or reload the editor. The Engine SDK migration is
separate and is not required or included.

## Purpose and prerequisites

Use it to create, write and save specification drafts in a browser, and to read Stories, catalogs,
decisions and Run & Test plans for a checkout on this computer. It needs an installed SFlow build on
local macOS; native Windows and remote forwarding are not qualified yet and are refused explicitly.

Spec Studio supports creating a business or technical draft, editing its wording and title, explicit
save (also Command/Ctrl+S), a safe preview, quality checks, saved versions and supporting sources.
IDs are generated by the existing specification owner. Catalogs, Decisions and Run & Test currently
expose canonical read results. Management edits, imports, activation, application/test execution,
person-only review, publication and approvals continue through their existing native surfaces during
this rollout. These read pages do not claim completed management-menu migration.

## Use it from each surface

- **Shell:** `singularity-flow ui open` from the intended checkout; `singularity-flow ui status --json`, `singularity-flow ui stop [--drain]`
- **Copilot:** `/sf-ui` inspects status and shows the native opening routes; it never opens, serves or shuts down the service.
- **VS Code:** Command Palette → **Singularity Flow: Open SFlow in browser**, also a pinned shortcut.

The native commands are:

```text
singularity-flow ui open [--no-open] [--idle-minutes 1..60] [--resume-request INVOCATION-ID] [--json]
singularity-flow ui status [--json]
singularity-flow ui stop [--drain] [--json]
singularity-flow ui serve [--idle-minutes 1..60] [--json]
```

The CLI uses the runtime that launched that installed SFlow build. VS Code launches its selected SFlow
CLI/runtime pair, never code from the Story's repository. `serve` is a foreground diagnostic host, not
a workflow phase.

`ui open`, `ui serve` and `ui stop` are the person's own steps: no chat runs them, a plain chat
included, so a model turn never receives a browser bootstrap grant. Nor does any chat read a
specification with `--for-person`, the person's own view of its secret-shaped values. `ui status`
stays available to any chat.

## Guided workflow

1. Open the workspace from the checkout you mean, in your terminal or VS Code. The CLI opens a private
   page in SFlow's state folder that forwards to a one-use link; the link is never a process argument,
   and the page is removed once the link is used or expires. `--no-open --json` returns the link
   without launching a browser. Its fragment ticket expires after one minute, is removed from browser
   history on exchange, and is not a native control credential. Do not share this link.
2. Create or open a specification draft in Spec Studio and write. Saves retain the draft's sequence and
   operation ID; a stale edit is refused while unsaved text stays in the tab. Compare the newer writing
   or save your version as a separate draft. A lost save reply can be checked against the original
   snapshot without repeating the save.
3. Attach supporting documents or images, up to 5 MiB per file in the browser. They use the existing
   local source store; only descriptors may later travel with a shared specification. A missing
   original requests the matching file on that computer.
4. Search the Stories with checkouts on this computer, sort them by their column headings (creation
   date descending by default) and open one in this tab. For a Story available on the remote,
   attach it with `singularity-flow session open <WORK-ID>` or the VS Code Story picker first.
   Once selected, a Story's Run & Test results and Decisions come from its workflow checkout.
   If the Story spans repositories, Code Explainer and the application plan follow the repository
   you opened. Open the primary checkout for Ask questions about the Story record.
5. When a matching VS Code window is connected, **Continue with Copilot** prepares the existing
   `/sf-spec-author` request in that window. The person chooses Send. Delivery is not model execution,
   completion, acceptance or approval. A disconnected or different-checkout editor connection is refused.
6. Run `singularity-flow ui stop` when you are done, or let the service stop by itself after its idle
   period. `stop` refuses while operations are active; `--drain` stops accepting new work and lets
   admitted operations finish. There is no PID-based force-kill command.

## State and safety

Each tab has its own context handle, even though browser cookies are shared. Browser requests never
carry arbitrary checkout paths, shell commands or CLI argument arrays. Canonical operations run
with the explicit context root; this service does not change a process-global working directory.
Eligible reads reuse SFlow's private read workers. Other owners run through an isolated canonical
CLI child, with models disabled and original errors retained.

The service binds only to `127.0.0.1` on an assigned port. It has private native discovery and
credentials beside the workspace registry, under `browser/`. This is transport metadata, not another
Story/state store. `SINGULARITY_FLOW_UI_ROOT` redirects it for isolated qualification. No source,
worktree or original document is copied into the service's metadata directory as permanent state.

The native client's environment is scoped to its own grants and workers; another window does not
inherit its credentials or identity. Raw environment values stay in memory, outside browser
responses and transport receipts; variable names a shell exports that no process looks up by name are
left out. Diagnostics, original errors and progress are redacted before the browser sees or a receipt
keeps them. Changed credential scopes cannot reuse an old write receipt.
Startup and the service lifetime use the existing fenced lease owner, including its PID-start check.
Native control uses authenticated request/response proofs and encrypted inputs. A process reusing
an old loopback port receives neither the native credential nor the client's environment. The
editor reads the exact private discovery path returned by its CLI, including custom state locations;
opening a second browser tab keeps the first tab's matching editor connection.

Routine JSON control requests are limited to 256 KiB. Wording and local file bytes use separate
bounded content routes, with a 5 MiB upload limit. Activity lists return summaries instead of
retransmitting previous document bodies.

The default idle timeout is 10 minutes, configurable through `--idle-minutes` on startup or
`SINGULARITY_FLOW_UI_IDLE_MINUTES`, from 1 to 60. A compatible existing instance retains its current
timeout. Active work prevents idle shutdown; an open tab's status poll does not, unless that tab holds
writing it has not saved. Closing the editor does not kill the service.

Requests have stable invocation IDs, separate from HTTP attempt IDs. The browser inspects the
original receipt after a lost reply. A service restart marks unfinished transport records unknown;
it does not repeat mutations or infer whether they succeeded. A write whose canonical process was
cut short, or ended without SFlow's own answer, is unknown too. Receipts on disk keep a write's
identifiers only; read results stay in the service's memory. The canonical draft/history/result
remains authoritative. A token, checkbox or browser session never substitutes for the existing human
signer.

## Troubleshooting

- *The link expired or was already used:* reopen through the CLI or editor; each link works once, for one minute.
- *A reply was lost or a write is unknown:* `singularity-flow ui status --json` lists unresolved records and recent writes, including completed writes whose browser reply may have been lost; `singularity-flow ui open --resume-request ID` reconnects their original client and context for inspection. The write is never repeated automatically.
- *`UI_BUILD_MISMATCH`:* another build owns the service, including the same build installed at another path. Only a service from the launching engine is reused, and VS Code loads its editor bridge from its own selected engine. Drain it with its existing build (`singularity-flow ui stop --drain`), then launch the new build. A development checkout is identified as such; equal package versions alone do not establish build alignment.
- *Windows or a remote session is refused:* native Windows ACL and process-lifetime qualification, remote port forwarding and embedded views are unreleased. The existing CLI and VS Code panels stay available.
- *A service failure:* the original code and deadline are kept, with local-service recovery, without sending a person through unrelated Story diagnostics. This preview does not add automatic installer artifact cleanup or modify workspaces or recovery.
