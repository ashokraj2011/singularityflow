## Gaps and risks

### Stage 2: the opening operation

1. **Openings never leave the machine.** `phase begin`, `rollover --confirm` and `prepare` save the open version with no commit or push. Two clones can each open version N+1, and the clash shows only when one of them publishes, after the work is done. AC-015 cannot pass as the code stands.
2. **An opening can be shared by accident.**
   - Every governed commit includes `workflow.json`, and with it any open intent.
   - Narrow commits made during authoring would not include the `context/generation-start/…` receipt; the decision commands use `exactWorkItemPaths`, for example.
   - Reading the code, a second checkout would then see an open intent without its receipt, and `verifiedIntentRecord` would refuse with `GENERATION_INTENT_REQUIRED`.

   **Unresolved:** this is not reproduced yet. Stage 2's journey H must reproduce it before the fix.
3. **What the opening reuses, and what it still needs.** It reuses `commitAndPublish` with `exactWorkItemPaths` (`workflow.json`, `STATUS.md`, the start receipt and the consent receipt), a leased push and pending sync. That gives one winner, and conditional acceptance on the Story branch. Still needed:
   - a stable operation ID whose replay returns the original outcome;
   - the high-watermark advanced inside the opening;
   - a new lifecycle event type for an opening, which affects ledger event types and older readers (AC-019);
   - checkpoints a later turn can look up by operation ID.
4. **Consent has no receipt.** The guard holds `--confirm` to a "yes" kept in a per-turn file. It matches the model-written question by pattern, without the version number or the digest. Identity comes from Git or `gh`, or from SF Guard only where a Story's pin turns it on. Confirm codes stay on the machine that issued them.
5. **Takeover has no fence to reuse.**
   - Takeover says `exclusiveOwnership: false`.
   - The subject lock covers one clone, the session one worktree, the Story index one machine.
   - The only fence between hosts is the Story-branch lease at publication.

   A fence token has to live in the opening record and be bumped by a leased commit at takeover. Guards may not run Git on every tool call (REQ-041), so an old writer is refused only at entry and at consequential boundaries: publish, retain and submit.

### Stage 4: reviewer delegation

1. **Independence is asked for, not enforced.** SFlow cannot verify a fresh reviewer context. In VS Code the sub-agent shares the author's session, and its calls are told apart by heuristics: a frame file, a prompt prefix and a 30-minute frame.
2. **A missed attribution changes the reviewer's permissions.** The reviewer agent declares `edit` and `bash`, so read-only depends entirely on the guard attributing its calls to the reviewer's turn. If that attribution misses, the calls fall under the author's authoring contract.
3. **Retention proves less than §9 requires.** It checks only that the pinned agent differs from the author and that the binding is current. The human actor is the same person, and no dispatch mode or packet digest is recorded.
4. **No fallback outcome exists.** There is no capability detection and no "review pending, named capability required" result; only handoff text points to a new chat.
