# Approved plan and retained source-clause observations

The shared source-clause rule connects a reviewed planned obligation with an exact comment in a
delivered product path. It distinguishes an actual deletion, an unchanged tagged file, a missing
comment and a clause outside the Story's approved definition. A source comment alone establishes
neither test execution nor application acceptance.

## Ownership and compatibility

`plannedSourceClauseBindingsReplay` belongs to `kernel/code-delivery-evidence.mjs`. Its explicit
requests obtain specification records, the reviewed plan, secure path metadata, original bytes,
comment observations and source-origin facts. The rule owns allocation, clause selection,
namespace ownership and binding/missing results. The shared predecessor projection belongs to
`kernel/specification-policy.mjs`; the native specification export remains a compatibility alias.

The native adapter reads the exact absolute path returned by its existing security owner. It
retains the original 16 MiB limits and errors, planned-map pin verification, source-comment parser
and Git work-interval provenance. The existing carried-tag, Story-added-line and unchanged-tag
readers remain explicit compatibility owners. No native record, hash, error, authority, Git
behavior or returned source-binding shape changes.

An independent oracle captured at `155b0a49f` records 43 genuine native file/plan/origin cases
before extraction, including shared namespaces, carried and newly introduced tags, changed plan
pins, deletions and oversized source. Replay consumes the original ordered observations and is
also compared with the actual native adapter. The oracle is not regenerated from extracted rules.

## Namespace SDK inspection

The existing registered `phase.delivery.inspect` operation has a separately versioned
`sflow-delivery-evidence-inspection/v3` manifest. Its `clauses` group uses
`sflow-planned-source-clause-observations/v1`. Existing v1 and v2 port results remain readable with
their original strict fields and meanings; the operation count and engine contract do not change.

The namespace specification reader resolves the original approved plan and preceding definition
indexes through accepted publication/submission receipts and actual human approval thresholds.
It verifies deterministic specification replay before exposing the plan's content references.
An `approved` label or a supplied claim map cannot replace those proofs.

The source-clause reader supplies the shared rule with verified retained changed-file bytes and,
when needed, original archived bytes that match the unchanged current source snapshot. It reads
no checkout or process and writes no record. The host still checks current source observations,
retained evidence indexes, private draft identity and permission at the end of inspection.
Permission failures, unavailable content, corrupt evidence and real timeouts keep their errors.

Displayed obligations are complete rows within the requested entry and 64 KiB byte budgets.
Counts cover the full evaluated set, including omitted rows. Pending evaluation has null totals;
it is never represented as zero missing obligations. The manifest retains the exact original
plan, review-packet, definition-index and source-evidence content references without local paths,
source bodies or model prompts.

## Required integration still open

Shared namespaces need the source-tag origin owner before a portable Story can claim their tags.
Legacy unqualified paths spanning multiple repositories need an explicit repository-ownership
contract. These cases return named pending owners. Missing original/current archives have their
existing registered retain actions. No namespace reader fabricates successful provenance,
assigns one path to every repository or grants a phase approval.

The separate code-delivery, claim coverage, constitution, artifact-set, source-region and
execution/publication owners remain required. Full application publication and a complete
cross-agent Story, existing-project migration/cutover and distribution/performance qualification
keep Phases 5, 7, 8 and 9 open.

## Mac qualification

The final passing groups cover 313 distinct cases: 184 core, architecture and namespace cases;
98 native source/plan/delivery cases; and 31 installed offline package cases. The 13 source-clause
cases were rerun after bounding the invocation byte cache and are not counted twice. All groups
passed without failures, cancellations or skips. Earlier diagnostic failures were corrected in
the test host: required checks correctly precede the publication-owner refusal, and source
selection chains the actual accepted approval revision instead of requesting an unbound query.

The installed fixture reopens the same approved plan and source evidence from a different actual
checkout, with an empty PATH and Git/CLI imports denied. It still cannot publish application code
without the remaining owners. This is source/plan inspection qualification, not the complete
cross-agent application Story or an authority cutover.
