# Exact human article exceptions

The registered namespace operations `constitution.exception.context` and
`decision.constitution-exception` share a pure rule owner and an authenticated recorded-mutation
owner. They apply only to an active judged article in an exact submitted publication. An exception
does not waive an enforced machine policy, replace independent phase approval or modify an
already published artifact. Native Git records, ceremony, errors and authority remain unchanged.

Read the context with the exact article ID. It identifies the original Story source, configuration,
constitution content, article digest, publication, review packet and prior accepted exceptions.
The manifest supplies `expectedContext`, authorized phase groups and the actual recording state.
An unpublished generation routes to preparation; a publication without a submission routes to
submission. Closed and historical generations are read-only. Genuine missing-file, permission and
timeout errors keep their original identity and details.

Recording requires an explicit operation ID, phase, article, concrete scope and reason, and the
context digest. An optional expiry is an exact UTC ISO timestamp. Authentication uses the actual
current principal and configured phase approval groups. A configured person-presence requirement
still requires its real evidence owner and cannot be replaced by a caller's success flag. This
namespace decision has a distinct contract; it does not claim the native terminal ceremony.

The versioned exception retains its exact publication and original human receipt. The publication
and existing approvals stay immutable. Approval reconstructs the accepted decision chain and
checks the original article binding and expiry. An expired exception needs an authenticated human
renewal; renewal preserves both records. Reusing the original operation after interruption or on
another host returns its accepted outcome without a second decision or a new timestamp. No Git
commit identity is fabricated for a namespace record.

Filesystem, SQLite and application-store journeys exercise independent approval, custom phases,
shared-only replay, lost acknowledgements, expiry and renewal. Adversarial checks reject borrowed
authority, altered records and attempts to waive enforced policy. The offline installed SDK
completes the same flow without a checkout or a Git/CLI import, and NodeNext declarations require
the actual decision inputs. Original native constitution compatibility remains separately tested.

These optional SDK profiles do not activate production storage authority or admit mixed-version
writers; those remain Phase 8 work. Other Phase 5/7 owners remain in the
[completion ledger](ENGINE-SDK-PHASE-5-7-CLOSURE.md).
