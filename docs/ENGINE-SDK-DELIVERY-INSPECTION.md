# Candidate application delivery inspection

`phase.delivery.inspect` reads a private code generation's original-source archive,
changed-source archive and phase-check evidence through the public registry. It compares
accepted receipts with actual current source observations. The main namespace Engine and
the explicit `hosts/namespace-delivery-inspection` SDK export expose the same operation.

## Ownership and compatibility

The pure kernel owns test naming, runner ecosystem/root coverage, affected-path cohorts
and the bounded inspection manifest. The Node compatibility binding supplies explicit path
and runner primitives. Native delivery and test helpers use those same rule instances.
Ordinary files, symlinks, test execution and immutable evidence reads remain host observations.

The extraction preserves twelve independently captured native function-body fingerprints,
6,161 original path/runner outcomes, 219 actual native change-cohort outcomes and 51 executable
test-file decisions. The native baseline is `5309738f9`; the oracle is captured before extraction
and is not regenerated from the new implementation. Existing publication records and errors
are unchanged.

The namespace host coordinates accepted baseline, changed-source and check proof readers.
It validates the original operation/index bindings, compares each repository's current
application inventory, and repeats source, evidence-index, draft and access checks before
returning. Missing-file, permission, timeout, corruption and changed-context failures retain
their errors. Inspection needs `phase.source.inspect` permission and explicit source/local
working ports; it does not need the configured author role or writer permissions.

## Result and continuation

The namespace result contract is now `sflow-delivery-evidence-inspection/v2`; explicit v1 port
facts retain their original v1 result. The [shared source-analysis integration](ENGINE-SDK-SOURCE-ANALYSIS.md)
adds bounded clause-tag and exact test-declaration observations from retained source bytes.
It preserves separate identities for source, execution evidence and human acceptance.
Both profiles include compact
accepted record references, source/check match flags, protected/boundary counts and test
outcomes reconstructed from retained raw evidence. Test-root coverage uses actually passed
test commands for the same repository and the native ecosystem rules. A Node test command
cannot establish affected Python coverage. Root coverage is not clause acceptance.

`maximumEntries` bounds displayed paths and source-analysis file rows; complete affected/uncovered counts and final
freshness checks still apply. Zero is valid. No source text, raw test output, private physical
root or model prompt is included. A historical passing run remains recorded as passed when
source drifts, while `checksMatched: false` and its action require a new current run.

The kernel returns semantic actions for missing/stale evidence: `phase.prepare`,
`phase.draft.rebase`, `source.baseline.retain`, `phase.source.retain` and `phase.checks.run`,
as applicable. It returns missing required inputs and prerequisites explicitly. Original-byte
archival requires the original selection to remain available; current files cannot silently
replace those bytes. Failed checks require repair before another run. Adapters own command
rendering and human presentation.

## Remaining application publication work

The manifest explicitly states `observationsOnly: true`, `publicationReadinessInspected: false`
and `applicationAcceptanceEstablished: false`. It does not write records, execute tests, publish,
submit, approve or accept risks. An empty actions list does not establish publication readiness.
All native publication policy owners remain reported and required.

The existing code-delivery v2 policy requires committed/index/worktree/untracked origins and
rename detection. Filesystem snapshots do not supply those Git facts. No defaults are weakened
or caller-provided readiness accepted to bypass this gap. Full code/claim/constitution/artifact-set
policy integration, a complete cross-agent application Story, existing-project authority cutover
and final distribution/performance qualification remain required. Phases 5, 7, 8 and 9 remain open.

## Mac qualification

On Node 26.12.0, the affected namespace suite passed 103 cases, including original/current file
proof, real test execution, failing and stale evidence, independent readers, read-only publication
boundaries, bounded previews, current-source drift, access revocation and preserved real I/O errors.
All 67 architecture checks and 25 installed offline SDK-package checks passed. The installed
consumer reopens the actual query in another empty-PATH process and its declarations reject
caller-supplied readiness.

The eight affected native regression files passed 100 ordinary cases. Their five slow-lane cases
were then executed explicitly: the three relevant files passed 16 cases and the polyglot coverage
file passed 8, with no failures, cancellations or skips in those slow-lane runs. Together these
cover all 105 distinct native cases, including genuine delivery, configured runner journeys,
polyglot coverage and unsupported-runner refusals. No deferred journey is treated as a pass.

Source validation passed 3,929 checks across 191 skills. The first isolated home-folder name
accidentally matched a generic fixture email in the privacy audit; using a fixture-named home
removed that environmental false positive without changing product files or the privacy rule.
VS Code typechecking, the unchanged 2,011-site Git ownership audit and all 13 unchanged bundle
budgets passed. Gateway/extension module counts remain 852/152; Help/support/prewarm are
135/111/23. No budget ceiling was raised.

The isolated SDK build contains 56 registered operations, 173 owned modules and 1,715,132
JavaScript bytes. No Windows, hosted CI, live model, product install, real Story mutation or
authority cutover was performed. These results qualify this inspection and extraction slice,
not complete application publication or a product release.
