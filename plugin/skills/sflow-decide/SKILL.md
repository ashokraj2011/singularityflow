Each action: "<timing> — <label>", then its three separate Markdown bullets, in order: "- Copilot: `<copilotCommand>`", "- Shell: `<command>`", "- VS Code (model-free): `<modelFreeCommand>`". Keep returned routes exact; never apart from their label, on one line or in a table. Missing Copilot: "no verified equivalent"; missing Shell or model-free: "not available for this action". Never invent routes or make more calls for formatting. Run a check only when a returned field or command asks for it; never decide from a step's name, kind or route that it applies. <!-- sflow-turn-boundary: decision-only -->
**Turn boundary — decision-only:** `singularity-flow decision choose|applicability|scope|completeness|plan` (plan: `--add-location`/`--add-supporting` only), `singularity-flow upstream-issue decide|raise`, `singularity-flow decisions record` (issue options, after an explicit yes) and /sf-approve 1-6 are the only permitted mutations. Never edit files, run tests or builds, raw `git`, submit, reject or `next`. The person types every choice and reason; never supply, infer or default one. List answers come from `ask_user`; the person accepts or replaces each default. Any refusal ends this turn.

1. If `#sflowDecide` or `sflow_decide` is available, call it once with `workId` only: the person answers everything on its page and it records them, and its `remaining` is what's left. Then run `singularity-flow decisions <WORK-ID> --for-agent --json`, adding `--no-card` if neither is available. `data.recorded` is accounting, not visual review. A `routing-decision` item is answered at 2-5. For `action.humanReview`, use `#sflowWitnessReview` with `workId`, `criterion=clauseId`, `slot`; native UI alone asks checklist/reason. Unavailable: give `action.command`, never `/sf-decide` again. Report WIT ID or unrecorded; if recorded, refresh once; go on with what remains. No `action`: do 11-14; use its linked issue/owner, never duplicate; stop. Else give `action.command`, then run `singularity-flow decision show <WORK-ID> --json`. Empty routing is not approval readiness. Check pending routing (2), applicability (6), scope/completeness/plan (7-9), issues (10). If clear, show `ahead`; next `approval` (`data.next.kind`) you may approve (`decidedBy.allowed`): do /sf-approve 1-6 now, else give `data.next.copilotCommand`; stop.
2. Show `pending.label`, why it waits (`reason`, `round`, `maxRounds`), who decides (`by`), `values`, and every option: `id`, `label`, `toLabel`, `reach`, `skipLabels`. With `anyStep`, a step ID or `end` may be named instead.
3. Ask option ID/step and reason.
4. Run `singularity-flow decision choose <WORK-ID> --fetch --option <ID> --reason "<REASON>" --expected <pending.key>`, or `--to <STEP>` in place of `--option`.
5. Report commit, route, skipped steps, authority and phase; show `Next in Copilot: /sf-next`; stop.
6. For each `applicability` entry not `satisfied`, show `responsibility`, `declaredReason` and who decides (`authority`); ask why it does not apply. Run `singularity-flow decision applicability <WORK-ID> --fetch --responsibility <RESPONSIBILITY> --reason "<REASON>"`; report the commit; stop.
7. Scope statements: run `singularity-flow evidence scope <WORK-ID> --json`. For each `unresolved` item show `id`, `text` and `sourceId`; ask for a disposition (clauses for included or existing) and a reason. Run `singularity-flow decision scope <WORK-ID> --fetch --item <ID> --as <DISPOSITION> [--clause <IDS>] --reason "<REASON>"`.
8. Completeness review, only when `structurallyComplete`: ask for each article (completeness, ambiguity, consistency, verifiability, boundary-conditions, non-functional) as satisfied, exception or not-applicable. Run `singularity-flow decision completeness <WORK-ID> --fetch --confirm <inventorySha256> --article <ID>=<DECISION>... --reason "<REASON>"`. A review, not proof of correct scope.
9. Options with `chat.command` (a path no plan row names, a scope statement, a responsibility): `ask_user` with their `label`s plus Not now, then the reason and any clauses. Run that `chat.command` once with those at `<REASON>` and `<CLAUSES>`; report what it recorded; go on to the next item.
10. For `singularity-flow upstream-issue raise`, ask what's wrong (20+ characters); use their words. For existing issues show `id`, `phase`, `about` and allowed outcomes. Ask outcome, reason and any required PRC/FAM link or expiry; run its returned `singularity-flow upstream-issue decide` command with those answers. Never duplicate a linked issue.
11. Lead with `data.headline`; show each item's `title` and `why`. Not yours (`decidedBy.allowed` false): say `decidedBy.words`, give `decidedBy.share`, skip it.
12. Use the native review at 1 for `action.humanReview`; `chat.command` options at 9; otherwise `ask_user` per other item: option `label`s (recommended first) plus Not now, then each `needs` value with its `default`. `action` is theirs to do: give `action.command`; never record it.
13. Preview: `singularity-flow decisions <WORK-ID> --choose <ID>=<OPTION>... --for-agent --json`, adding `--reason|--expires|--cause <ID>=<VALUE>` only for changed values; show `data.preview.summary` and `refused` `words`/`share`.
14. `data.preview.withApproval.recordInChat`: after an explicit yes, do /sf-approve 1-6 now with `withApproval.flags` on its approve command (one commit). Else `data.preview.record.recordInChat`: after an explicit yes run `data.preview.record.command` once, exactly; report IDs and remaining items; if `data.remaining` is only `approval`, do /sf-approve 1-6 now. Else `data.preview.record.chatSteps`: run each `command` once, exactly, one at a time, then read the list again. Otherwise give the person `withApproval.command` or that command for their own terminal (reused runs and test-run risks are theirs to record). Never edit a digest; `DECISIONS_PACKET_CHANGED`: show the fresh list, restart at 11.
