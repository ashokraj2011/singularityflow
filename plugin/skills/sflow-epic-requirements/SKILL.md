# Build the Epic Requirements bundle

<!-- sflow-copilot-pause -->
Before any boundary lookup or SFlow action, run `singularity-flow pause status --json` and follow its `data.agentInstruction`. If `data.paused`, answer as native Copilot, only offer `/sf-pause off` and never resume implicitly. This skill is already loaded; never call the skill tool for it. Unless paused, continue below in this turn.

<!-- sflow-output-contract: clarification-and-artifact -->
**Output contract:** Author configured artifacts from governed inputs and pinned clarification; publish only after readiness. Approved phase inputs are the earlier steps' outputs and settle what they state: never ask what they answer or search elsewhere for them. A publication returning `reviewSubagent` is reviewed next: start that reviewer as a sub-agent here, in the foreground, as its `instruction` says (no sub-agent tool: its new-chat route); relay no route while it runs, and ask a code offer only after a ready review; never review, retain or submit it yourself. Summarize artifacts with verified Markdown-preview links; never paste document bodies, code or diffs into Copilot. For code, list touched paths and observed added/deleted/created line counts; unavailable stays unavailable. Use existing evidence, not extra calls solely for display. Summaries, links and opened previews are not human review or approval. Each action: "<timing> — <label>", then its three separate Markdown bullets, in order: "- Copilot: `<copilotCommand>`", "- Shell: `<command>`", "- VS Code (model-free): `<modelFreeCommand>`". Keep returned routes exact; never apart from their label, on one line or in a table. Missing Copilot: "no verified equivalent"; missing Shell or model-free: "not available for this action". Never invent routes or make more calls for formatting. When a result's `act.state` is `author`, or it routes back to this skill with nothing for a person to answer, edit, review or confirm, that is this turn's own work: do it, never relay it. Copy every line a patch matches, changed or unchanged, from the file as it is now, read after your last edit of it, never from memory, a finding or a search result; one file per patch, so one stale hunk cannot reject the others. A file edit that does not match is not a refusal: read those lines again and redo the edit. Where the steps say ask_user, use your host's question tool: ask_user in the Copilot CLI, vscode_askQuestions in VS Code; it is unavailable only when neither exists.
<!-- sflow-execution-boundary -->
**Boundary:** no Story required; cwd=opened Git root or verified `repositoryPath` from `singularity-flow workspace current --json`; refuse if neither resolves; never search `$HOME`/parents. Use exact CLI-returned paths. `repositoryPath` is command cwd, not a prefix for absolute file paths. Never rebase paths or strip `.git/worktrees`. Issued private/external files are exact exceptions to repository confinement, not wider read/write permission; writes still need authorization. Resolve relative paths only against their declared base. On failure, preserve the path and error; never search or recreate it.

1. Run `singularity-flow epic requirements status --json`. Epic Intake accepts the Jira identity and pinned sources automatically; do not build or request a repository world model on `main` or the Epic branch.
2. List pinned inputs with `singularity-flow epic sources list --epic <EPIC-KEY>`.
3. Record every business note with `singularity-flow epic sources note --text-file <FILE>` and every accepted Copilot answer with `singularity-flow epic sources answer --text-file <FILE>`, writing FILE only at the source-text draft this turn's rules name, one at a time. Never leave accepted answers only in chat history.
4. Run `singularity-flow epic requirements prepare`. Read the complete governed context that it prints: phase contract, governed agent, Jira snapshot, pinned sources, question ledger, and workspace repository registry. Repository grounding is added later, after each Story has its canonical branch.
5. Use `ask_user` to ask one concise batch of material questions and wait. Even when the pinned evidence looks complete, ask the contributor to confirm your concise interpretation of outcome, boundaries, and acceptance criteria. If `ask_user` is unavailable, display the questions and stop before authoring or publication. Record every accepted answer with `singularity-flow epic sources answer`, rebuild context, and continue. Unanswered questions stay visible; never fabricate scope.
6. Author every output at the exact path `singularity-flow epic requirements prepare` lists (by default `requirements.md`, `traceability.yml` and `impact-analysis.yml`). Use stable `REQ-nnn` and `AC-nnn` identifiers and cite exact `SRC-nnn` evidence.
7. Run `singularity-flow initiative phase draft-check epic-requirements --initiative <EPIC-KEY> --json`. If unready, act only on its `findings` and `correction`, rerun its `commands.recheck` at most twice, and stop on an unchanged `draftFingerprint` (an unedited draft); same findings after an edit: correct differently. Only when `status` is `ready`, run `singularity-flow epic requirements publish`, summarize every output with verified preview/file links and hashes, and stop for human review of the complete bound documents outside chat. Do not reproduce bodies or infer review from links.
8. After explicit approval, hand off to `/sf-initiative-approve <EPIC-KEY> phase` for its receipt and self-approval flow. Never approve automatically.
