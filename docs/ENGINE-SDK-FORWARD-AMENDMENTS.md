# Namespace forward amendments

The namespace host now binds proposal, human decision and reader revalidation to the same registered
operations as the Git adapter. Native target selection and direct-reader selection share pure
kernel rules. Captured pre-extraction results retain the original native values and refusals.

## Ownership and retained evidence

The kernel chooses eligible historical documents and computes transitions. The SDK verifies the
original publication, submission, human approvals, configuration and consumed input bytes. One
conditional mutation coordinator persists the proposal or decision through SDA. A proposal takes
an explicit device-local output draft reference; accepting its deliberate replacement retains those
output bytes as shared evidence. Uploaded input documents remain local.

An approval produces actual publication v5, submission v6 and human-vote v3 records inside that
decision's transaction. It does not synthesize publish, submit or approve operation receipts. The
original generations, source bindings and votes remain immutable. The current phase stays in place;
its approved direct readers owe an explicit unchanged or return decision. Required ordinary policy
evidence is constructed in memory and retained by the same conditional writer.

A non-producing document review has its own versioned intent-context manifest. It authenticates the
actual approved specifications and plans; it cannot define clauses, amend a plan or establish Code
acceptance. Forward returns consume the original pinned repair budget. Code history v11 carries an
actual reader return; v12 carries the reapproved reader into first Code. Code policy v28–v31 admit
those histories, optional human acceptance and repository coverage. Frozen v1–v27 meanings remain
unchanged, as do ordinary publication, submission and vote writer profiles.

## Supported paths and limits

Use `forward-amendment.propose`, `forward-amendment.decide` and
`forward-amendment.revalidate` through `engine.run`. `decisions.list`, `story.next` and
`story.guide` expose the real owed ceremony. An upstream `amend` disposition authenticates the
actual accepted proposal, producer and owner; it does not add a second decision for the same gap.

Clause-defining and planning owners retain their intent-amendment and plan-correction routes.
Multi-vote amendments, fresh-test ceremonies and policy owners without a bound implementation keep
their explicit return or rejection routes. Missing files, permission errors and actual deadlines
remain distinct. Reusing an operation ID reconciles its original transaction and does not repeat
a replacement generation, vote or repair-budget charge.

## Mac qualification

Tests cover filesystem, SQLite and application storage; independent approval; unchanged and returned
readers; initial and later Code; actual fresh Node tests; Release; constitution evidence; exhausted
budgets; upstream amendment association; lost acknowledgements; and shared-only replay. An offline
installed consumer verifies the amendment and reader without Git, CLI, local drafts or a new clock.
No Windows, live provider, production Story or installed authority migration is part of this work.
