Specification quality asks "is the requirement good enough?", which is a different question from verification ("does the implementation satisfy it?") and from conformance ("does the evidence trace to approved intent?"). `sflow spec analyze` answers the deterministic part without a model: unresolved clarification markers, duplicate requirement text, missing scenario sections, and defects the clause extractor refuses. It never claims prose is complete, clear, consistent or correct, and it says so in its own report — a clean run means nothing checkable is wrong, not that the specification is good. `--assisted` adds semantic candidates through one governed model turn with no tools; candidates are observations for a reviewer, are recorded separately with the model, prompt hash and usage, and change no deterministic finding and no gate.

Write `[NEEDS CLARIFICATION: your question]` wherever you would otherwise be guessing. A phase pins a marker policy of `off`, `warn` or `block` separately from its conversational clarification mode. Under `block`, an unresolved marker stops publication and submission before any state changes, so an honest question costs only the answer. A marker is resolved only when a later generation removes it **and** the answer is on record — deleting the question is reported as an integrity concern, not as progress. Record the answer with `sflow clarification record <phase> --marker "<the question>" --answer "..."`.

Every approval of a checklist-governed phase records one decision per required article: `satisfied`, `exception` or `not-applicable`, using `sflow approve <phase> --article <id>=<decision> [--article-reason TEXT]` or `--checklist <file.json>`. An exception needs a human-authored reason and, when the phase configures one, membership of a named exception authority. There is deliberately no flag that answers every article at once. A phase may also declare a typed artifact set: its members are hashed individually and the approval binds the whole bundle, so `sflow reject <phase> --member plan.md` reopens named members and the next publication reports anything else that changed. `tasks.md` is derived from the approved specification and plan by `sflow spec tasks` and is advisory — ticking its boxes is never evidence.
