# Registered decision lists and recoverable namespace batches

`decisions.list` is a read-only registry operation. The native CLI keeps its existing card,
commands, JSON and decision protocol in the host; the SDK returns detached policy values and
structured actions. Native reads use the narrow query owner. The ordinary API also routes
`scope.context` through that read composition rather than an unbound mutation composition.

## Ownership and contracts

The kernel owns list binding, answer validation, authority selection, explicit checklist answers
and route-last ordering. The namespace reader reconstructs the source inventory, current private
specification, accepted human decisions, actual test-command requests, original upstream issues,
conformance reports, route question and retained witness candidates. Permission to read a list
does not authorize a decision. Fresh identity, permissions, private bytes and Story revision are
checked again; a list never records approval or visual acceptance.

The namespace host binds `decisions.record` to the same Engine's registered domain operations.
It does not create another engine or dispatch a CLI. Scope, completeness, applicability, upstream
accept-risk/dismiss, test-command acceptance, conformance gaps and route choices retain their
original domain transactions, immutable receipts and authority checks. A partial verdict linked
to an upstream issue exposes the original issue/owner, without a duplicate conformance decision.

Batch body, reference and outcome have explicit immutable v1 record families. Runtime storage
holds the reviewed intent and final acknowledgement, conditional on the actual authority, head,
configuration and source-read versions. The reviewed private specification bytes are retained
only when a human starts an actual batch. Uploaded input documents and images remain local.
This runtime journal does not write the Story head or replace any domain receipt.

## Interruption, concurrency and takeover

A retry authenticates the original reviewed source and accepted prefix. Lost replies after intent,
a domain commit or completion preserve the genuine error and deadline details. Exact retries
reconcile the original receipts and do not duplicate decisions. Another operation between effects
preserves the accepted prefix and requires a fresh review of the remaining list. Private draft
changes also refuse an old uncommitted suffix. Concurrent acknowledgements return the first
accepted outcome after verifying its actual recorded decisions. Replay preserves original time and the original decision agent while allowing the same human to
acknowledge an accepted batch from a different phase prompt, including after Story completion and in a shared-only process with no source or private store.

The native Git protocol intentionally retains its existing stale-confirmation behavior. The new
namespace replay contract does not silently change native receipts, hashes or approval authority.

## Human actions and remaining owners

Visual/inspection choices return exact published file identities from the existing witness owner,
including earlier eligible Code producers. They require a separate human witness context/checklist;
a batch cannot record a visual pass. Submission review similarly remains a distinct action.
Structured actions must name an actual registered operation and its accepted input fields.

This delivery does not implement forward-amendment publication/revalidation, obligation/evidence/test
risks, witness exceptions, live application comparison, automated test recovery or the remaining
external execution/evidence owners. These remain in the Phase 5/7 ledger. Neither phase is complete.
