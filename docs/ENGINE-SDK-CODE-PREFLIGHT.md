# Shared application-code preflight

The native `evaluateCodeDeliveryPreflight` adapter now drives one shared kernel replay. Candidate
eligibility, protected/source boundaries, generation reuse, fulfillment, criterion ownership,
source/test duties and stable finding identities are interpreted without discovering a repository,
reading a file, invoking Git or rendering a command inside the kernel.

This is the prepublication counterpart of [receipt replay](ENGINE-SDK-CODE-DELIVERY-REPLAY.md).
It preserves native Git behavior and approval authority. It does not publish, execute tests or
approve a phase. Namespace-backed application publication and migration Phases 5, 7, 8 and 9 remain
open; required publication-policy owners must still be implemented rather than disabled.

## Owners

| Owner | Responsibility |
|---|---|
| Kernel code-delivery rules | Candidate/change cohorts, protected paths, source boundaries, ordinary and returned-generation duties, exact fulfillment and evidence limits, preflight ordering and receipt/finding identities |
| Kernel phase policy | Code/review relationships, exact reviewer-return eligibility and semantic recovery offers |
| Kernel specification policy | Cumulative planned claims, allocations, criterion namespaces and lazy baseline-tag ownership |
| Explicit Node value binding | Fixed path/byte/hash primitives and test ecosystem facts |
| Native read adapter | Actual interval and plan bindings, change sets, committed/current bytes, secure file observations, lexical/witness analysis, required coverage and authenticated exception owners |
| Native presentation | Existing refusal wording, Copilot/Shell recovery commands and formatted repair details |

Existing specification, candidate-scope, finding and dispute exports share these rule instances.
Configuration and test-support paths retain their exact plan obligations while remaining separate
from product-source comment duties. Supporting files still pass the closed supporting-change
classification; an arbitrary source path cannot become support merely by appearing in that list.

## Ordering and failures

The rule replay requests the actual work-interval baseline before candidate inspection. A real
missing baseline, permission error, unavailable analysis owner or stale plan remains an error at
its original boundary. Optional baseline-test/reuse inputs do not remove current source safety,
claim coverage, test execution or human approval requirements.

Fulfillment consumes actual secure file-kind/size facts and bytes. Existing/evidence paths are
hashed by the shared byte primitive; removed paths must be absent; document/configuration work
must change its exact planned path. The retained-evidence size limit is checked before reading its
body. These checks do not accept a reader's passing verdict in place of the file facts.

Unknown-criterion handling requests carried baseline tags only when their shared namespace makes
ownership relevant. It retains the distinction between this Story's own tags, earlier Stories'
tags, exact witnesses and criteria absent from the pinned specification. The synchronous native
value API drives the same interpreter and invokes its explicit baseline callback only when needed.

When the kernel refuses, it requests formatting and then unconditionally throws the response.
A formatter returning `ready` cannot admit the candidate. The host continues to produce the original
errors, structured finding IDs, retained-evidence gaps and exact traceability-repair routes.
The separate claim-coverage owner remains required. Its `SPEC_COVERAGE_INCOMPLETE` error retains the
exact private repair candidate as a non-enumerable property, preserving the existing privacy and
recovery contract.

Source-clause/declaration analysis, authenticated disputes, reviewed baseline tests, exact reuse
and final specification coverage still have their existing native compatibility owners. They are
explicit required dependencies of this native composition; a new namespace host must supply
equivalent verified owners. Moving the coordinator does not prove those integrations complete.
Clause/index and verification values now have [shared kernel owners](ENGINE-SDK-SPECIFICATION-VALUES.md);
their actual approved-record reads and acceptance proofs remain separate requirements.

## Compatibility evidence

Before extraction, the unchanged native `c1fe0a6db` implementation produced the 33 outcomes in
`test/fixtures/code-delivery-preflight/native-v1.json`. That fixture records its original function
fingerprint. It covers ready/custom/legacy paths, excluded changes, source boundaries, symlinks,
source/criterion gaps and the different fulfillment duties. The new adapter must reproduce the
delivery bindings, finding identities, error order and recovery details.

Separate tests replay observed candidate facts after deleting the original checkout, reject a
formatter's attempted acknowledgement, retain real baseline/coverage failures and check the
private repair binding. Native source-binding, specification, candidate, amendment, dispute,
review-return and publication journeys qualify the existing production behavior. Architecture
checks enforce the pure dependency closure and one shared preflight path. Qualification is on Mac;
no Windows, CI, live provider, real user Story, install, merge or push is part of this extraction.

The final Mac qualification passed 285 affected regression cases, 18 journey/continuation cases,
71 architecture cases and 27 independently installed SDK checks: 401 tests with no failures,
cancellations or skips. The journey group includes all 13 opt-in slow-lane cases. Source validation
passed 3,948 checks across 191 skills; VS Code typechecking, the unchanged 2,011-site Git ownership
audit and all 13 unchanged bundle budgets passed. The gateway now contains 851 modules against its
existing 852-module ceiling. The preview SDK retains 57 operations across 184 owned modules and
1,793,147 JavaScript bytes. These results qualify this extraction, not complete namespace application
publication or installed authority migration.
