# Shared specification coverage and acceptance rules

Coverage, active-record selection, cumulative observed claims and specification acceptance now
have one kernel owner. Native publication and final checks use the same rule instances; the SDK
exposes their explicit-value and observation-replay contracts. This removes another native policy
dependency required for portable application publication. It does not activate another storage
authority or complete the remaining application runtime and migration milestones.

## Boundaries

`specificationClaimPolicies` owns cumulative fulfillment, test-only evidence, supporting-file
accounting, withdrawn clauses, missing source/test evidence, legacy acceptance identity and
candidate completeness. Its path and hash primitives are explicit. Active selection and bound
planning-owner selection live with specification policy. Native exports retain their names.

`evaluateSpecCoverageReplay` requests source existence and commit reachability only when the host
explicitly selects evidence verification. Each reply must be the requested boolean fact. A
`ready` object cannot substitute for it. The native synchronous adapter serves exactly those
reads with its existing filesystem and Git owners. An absent source in an actual deletion stays
distinct from unbound missing evidence. Exceptions thrown by a fact provider retain their identity.

`candidateSpecificationCoverageReplay` requests the actual original record set, excludes the
candidate phase's previous observed map, and preserves final-versus-earlier allocation. It yields
the existing late timestamp checkpoint while deriving the candidate's observed claims. The host
supplies an explicit logical application-path context; the kernel never discovers a checkout.
The result distinguishes ready, advisory and correction-required coverage. It has no rendered
Shell or Copilot commands. Native presentation preserves its current refusal text, private risk
candidate, upstream-decision route and non-blocking recorded-coverage advice.

Specification acceptance retains exact run hashes, command/source identity, generation, failed
commands and missing runs. Test-file presence remains presence; it does not become per-test
execution or human approval. Actual namespace source/plan/run admission and the global
verification-contract owner still have to bind their original accepted records before application
publication. The primary-document host continues to require its remaining named owners.

## SDK surface

The pure `specifications` entry provides the factory plus `codeCoverageEnforcement`,
`plannedClaimsForObservedPhase` and `selectActiveSpecRecords`. The optional `specifications/node`
entry binds the same factory's merge, coverage, acceptance and candidate replays to fixed Node
path/hash primitives. Neither entry reads Git, files, global configuration or a model provider.
These value utilities do not retain evidence or provide publication, submission or approval ports.
