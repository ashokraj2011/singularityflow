# Shared specification analysis and retained human checklists

Specification quality, clarification-marker reconciliation and scenario coverage now share pure
kernel owners. Native Git consumers retain their existing file reads, authoring boundaries,
records, errors and human authority. The explicit namespace Engine retains the actual analysis
through publication, submission, review and independent human approval.

## Ownership

| Owner | Responsibility |
|---|---|
| Kernel | Marker grammar, scenario structure, bounded findings, severity, policy hashes and checklist/exception rules |
| Declared content | Required section names and the exact checklist articles; no readiness callback or model prompt |
| Native compatibility adapter | Default review content, concrete UTF-8/hash primitives and existing exports |
| Native gate | Original artifact and clarification reads, followed by the shared value evaluation |
| Namespace policy reader | Reconstruct and verify reports from the original artifact, approved policy, lifecycle basis and predecessor publication |
| Namespace content retention | Store immutable reports and manifests; cannot accept lifecycle state |
| Publication/submission/approval owners | Conditionally bind the verified evidence and apply the existing authority and quorum rules |
| Host | Authenticate humans, display exact resources, obtain answers and render commands |

`specificationAnalysisPolicies(values, declarations)` exposes explicit-value analysis through the
SDK's pure `specifications` entry. The declarations have the versioned
`sflow-specification-analysis-declarations/v1` identity. They contain bounded section names and
checklist content, captured by value. Hash/byte primitives use the existing UTF-8 value contract.
The optional `specifications/node` entry supplies the default native binding.

The deterministic report preserves the existing `specification-quality-analysis` schema 1,
including its disclaimer: structural findings do not prove semantic completeness, correctness,
test execution or human review. Scenario hints retain their advisory status. Marker severity is
evaluated separately, so one unresolved question does not become two different quality failures.

## Versioned retention

| Record | Compatibility and added meaning |
|---|---|
| Publication manifests 1/2 | Original primary-document/check profiles and bytes remain unchanged |
| Publication manifest 3 | Original specification/plan profile remains unchanged when analysis is absent |
| Publication manifest 4 | `sflow-policy-publication/v1`, with actual typed policy evidence and optional check/specification proof |
| Phase-policy binding 1 | Identifies one typed immutable evidence manifest; a binding alone grants no readiness |
| Specification-analysis manifest 1 | Binds original artifact, actor, draft, configuration, accepted basis, predecessor publication and report |
| Approval artifact set 1 | Original primary-document set remains unchanged without a checklist |
| Approval artifact set 2 | Binds the human checklist outcome to the exact analysis evidence and submitted packet |
| Human vote envelopes | Original ordinary v1 and routed v2 formats remain unchanged; their artifact-set digest binds the new evidence |

Publication manifest 4 requires a bounded, nonempty list of distinct policy kinds. The current
reader implements `specification-analysis/v1` and the separately qualified
`clarification-checkpoint/v1`; an unknown kind or future record/report version
requires its matching reader. Invalid identities or altered report bytes are corruption.
Missing blobs, genuine permission failures and timeouts retain their specific errors.

The reader reconstructs the original lifecycle basis and pinned configuration, reads the actual
artifact bytes and reproduces the report. Earlier generations use their real accepted publication
proof. The accepted publication plan must contain the original basis and required evidence
references. Private verification is tied to the exact publication object and canonical identity;
copying it, mutating it or changing it during an awaited read cannot acquire proof.

Only this verified proof satisfies the `specification-analysis` owner. It does not satisfy a
clarification response, code delivery, test execution, constitution, source review or any other
unbound policy owner. The [retained clarification owner](ENGINE-SDK-CLARIFICATIONS.md) now supplies
actual accepted marker answers through its own proof. A marker still present in the authored text
remains open. Removing a previously published unanswered marker retains the discrepancy.

## Author repair and human approval

Enforced structural defects return `ARTIFACT_AUTHORING_INCOMPLETE`, with the exact logical artifact
key, findings and `phase.draft.write` operation. The existing private draft and Story remain in
place. Repairing the authored document does not require creating another Story or changing
approved upstream records.

Submission retains the publication's existing proof. `phase.review.resources` issues the exact
readable `story-document` reference for its analysis report alongside the submitted packet and
primary artifact. `document.read` reads that reference; consumers need no inferred laptop path.
Older profiles without analysis retain their existing resource list.

When enforced, checklist answers come from the authenticated human. Missing answers return
`APPROVAL_CHECKLIST_INCOMPLETE`, the article questions and the same bound `phase.approve` action;
no approval is recorded. Malformed answers retain an explicit input error. The existing
membership, independence, self-approval and threshold rules remain necessary. Reasoned exceptions
also require the pinned narrower exception authority when one is configured.

Accepted answers are retained in the versioned artifact set and replayed against their original
policy, report, actor and packet. The conditional approval plan must name the policy evidence.
Retrying the accepted decision acknowledges its receipt; supplying different answers cannot
rewrite it. Advisory mode retains disclosed warnings without upgrading them to semantic proof.

## Qualification and remaining migration

The regression fixtures compare independently captured native analyzer and gate/checklist outcomes.
Actual namespace journeys cover filesystem, SQLite and application-journal stores, human authority,
author repairs, rework history, exact review references, altered/future records, read failures and
receipt replay. The installed tarball authors and approves a specification/plan journey in a
separate empty-PATH process and reopens the original evidence without the old checkout.

Mac qualification on Node 26.12.0 passed 344 distinct affected tests: 94 native/value cases, 146
namespace lifecycle cases, 75 architecture checks and 29 installed-package cases. The native
oracles retain 94 analyzer/marker outcomes and 54 gate/checklist folds. The final native group
also exercises the remaining context-envelope helper directly, including count, byte and excerpt
truncation. No final group contains failures, cancellations or skips.

Source validation, VS Code typechecking and the unchanged Git ownership audit passed. All 13
existing bundle ceilings passed without increases: gateway 851/852 modules, extension 152, Help
135, support 111 and prewarm 23. The optional SDK retains 57 operations across 200 owned modules,
emitting 1,993,814 JavaScript bytes. These are compatibility and packaging results, not complete
application-Story or Windows latency measurements.

This extraction does not complete production policy/execution integration, full application Story
execution, existing-project migration or authority cutover. Migration Phases 5, 7, 8 and 9 remain
open. Installed Git projects are not migrated by importing the namespace Engine. Windows, hosted
CI, live providers, real Stories, product installation, push and merge are outside this local
qualification.
