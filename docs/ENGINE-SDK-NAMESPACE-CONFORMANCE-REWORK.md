# Namespace conformance evidence and Code rework

This opt-in Engine slice adds release/conformance evidence and an authenticated Code successor.
Kernel rules own row interpretation, contradiction checks and disclosure rules. Namespace readers
own reconstruction of accepted publications, submissions, source archives and human approvals.
Content retention and conditional lifecycle writes use the existing SDA ports. SGOS still owns
actual test execution. Native Git behavior and installed authority remain unchanged.

## Conformance publication

A `conformance/v1` policy binding accompanies the existing v4 publication envelope. Its immutable
manifest and `sflow-namespace-conformance-policy-report/v1` report bind the original artifact,
configuration, lifecycle basis, approved definitions and exact Code producer evidence.

The supported phase is artifact-only, has verification/review responsibilities and declares its
Code inputs. A verification responsibility also pins `testEvidenceFrom`; ordinary inputs being
disabled does not remove that dependency. Each repository keeps its own observed claims, retained
checks and acceptance witnesses. Carried test evidence belongs to its producing generation; a
consumer without an execution retains `checks: null`.

Every approved clause needs a qualified table row. Missing, unknown and duplicate rows, invalid
verdicts, undisclosed self-approval and contradictory table/prose findings require correction.
A matched row must agree with retained observed delivery. Acceptance criteria additionally need
actual successful declaration witnesses with their logical test IDs. A summary saying that tests passed is insufficient.
The native report rules use the same pure owner without changing their existing issue hashes,
priorities or approval deadlines.

Partial, missing or deviated rows stay honest in the retained report. Their gaps identify the
original Code owners; detection does not transfer ownership to Release. Publication and submission
do not invent a human decision. Final approval either uses an authenticated configured return to
an owner for repair, or uses the exact upstream-owner disposition described in
[human decisions and reviewer returns](ENGINE-SDK-HUMAN-CONFORMANCE-REWORK.md). An undecided
terminal partial produces `ENGINE_CONFORMANCE_DECISION_REQUIRED` and the bound conformance-context
action. The new receipt does not change the report's verdict or certify another test run.

Authoring and review manifests issue the exact conformance report reference as a shared document.
Another device can verify retained evidence without the first device's private draft or checkout.
A new publication still checks the selected live sources and final authority/lifecycle bindings.

## Code successor

Existing `code-delivery/v1` manifests/reports keep their generation-1 meaning. A successor uses
`code-delivery/v2` for configured loops, with version-2 manifest/report formats and preflight.
Reviewer-requested returns use the separate `code-delivery/v3` profile described in the human
decision extension. Its history
binds the exact predecessor publication, policy/report and original human-approved return.

Opening rework authenticates the original submitted packet, human identity/quorum, recorded route,
change request, invalidation marker and accepted lifecycle transaction. A copied request or an
altered return cannot authorize source changes. The checkout must initially match the exact
approved predecessor delivery. Preparation keeps the original Story source selection and baseline
for cumulative change accounting; it does not treat already-delivered Code as an unexpected edit.

The successor records the actual application/test inventory differences since its predecessor.
It independently revalidates the complete delivery against the original baseline, approved plan,
source comments, implementation regions and acceptance contracts. New exact-source test evidence
is required. Tests from generation 1 cannot become a generation-2 execution. A test-only repair
can retain unchanged product source while explicitly showing the test changes.

Approved return and predecessor records remain immutable. Every original publication is verifiable
through its accepted binding and retained content after later generations and checkout removal.
The current-generation document API retains its existing selection/stale-reference behavior;
this slice does not add a historical document-selection API.

The supported return is a configured, human-approved loop to the same original Code phase, with
one open original change request and the same repository selection. New source selection during
rework, unchanged revalidation, initial Code after other phase rework, other Code-producing predecessors, surgical member/clause returns and ask-choice routes,
shared source-line origins and advanced acceptance/risk contracts still need their named owners.
There is no default exemption for an unknown configured owner.

## Qualification and migration boundary

Qualification uses isolated local projects, storage, identities, source archives and actual Node
executions. It exercises independent approval, conservative partial verdicts, original-generation
replay, altered returns/reports, and continuation without the old checkout. Mac results are recorded
in the migration plan after the affected checks finish. No Windows, hosted CI, live model or real
project mutation is part of this delivery.

The core release cases pass on filesystem, SQLite and application stores, including original
producer attribution, readable retained reports, corruption/future-schema refusal and shared-only
replay. A separate terminal-partial case preserves the submission and refuses to invent a human
disposition. The rework journey passes on all three stores, with fresh generation-2 checks,
rejection of copied/altered returns and original-generation replay. The pure rule cases reject
missing logical test identity as well as unsupported matched labels and contradictory rows.

The larger grouped qualification attempts reached a 20-minute harness deadline. Interrupted
cases were left unqualified and moved to independent per-backend entries with unchanged case
bodies; backend drivers bound each file rather than the whole matrix. The database rework cases
took about 17 minutes each under the concurrent qualification load. They establish correctness,
not acceptable production latency. Read/proof traversal performance remains a migration gate.

The installed SDK qualification passes nine actual checks across two offline-packed journeys.
Each durable phase runs in a fresh process with the existing 60-second child limit and a
120-second test limit. Conformance takes about 53 seconds across three process stages; rework
about 142 seconds across six. The longest stage is about 46 seconds. These are correctness and
resume checks, not latency benchmarks. The initial combined journey exceeded the child deadline;
no timeout was raised. Whole-Story single-process latency and packaged SQLite-journal performance
remain unqualified. The existing installed-package qualifier retains its original bounds. Its first aggregate attempt
exceeded 120 seconds; conformance-only fingerprinting was then removed from the legacy consumer
path. All 34 installed checks passed on rerun in about 118 seconds. That small margin remains a
performance qualification concern; no deadline or bundle limit was increased.

Mac qualification records 229 distinct successful affected cases, counting repeated cases once.
The interrupted aggregate cases were rerun in focused entries; completed earlier cases remain
part of the evidence. Source validation passed 4,060 checks across 191 skills, architecture and
schema-contract checks passed, and VS Code types and the unchanged 2,011-site Git audit passed.
All 13 unchanged bundle ceilings passed; gateway remains 852/852 modules, 6,920,659 bytes.

This is a supported application profile, not completion of the SDK migration. Phases 5, 7, 8 and 9
remain open for the other production owners, complete cross-agent workflows, installed-project
cutover and final distribution/performance qualification. No merge to main is authorized.
